# agentic-tty 架构设计

## 1. 定位

一个以**伪终端（PTY）会话**与**子进程会话**为核心能力的守护进程，让调用方（AI Agent、脚本、人类）能像真人一样驱动交互式程序：起会话、发按键、等提示符、读屏幕。

- 跨平台：Windows（ConPTY）/ Linux（openpty）
- 双会话形态：`pty`（终端屏幕语义）/ `subprocess`（字节流语义）
- 多接入：MCP / CLI / Web，客户端可与守护进程分离部署
- 单一真源：会话输出以原始字节流为准，屏幕等皆为派生视图

## 2. 设计原则

1. **严格单向依赖**：层与层之间只能由外向内依赖，由 AST 扫描测试强制，不靠自觉。
2. **依赖倒置**：核心层定义端口（Protocol），运行时层提供实现；核心层不 import 任何原生扩展。
3. **单一真源**：会话输出以输出字节日志为唯一真源，其余查询皆为派生视图。
4. **单线程所有者 / 单一写者**：终端模型与日志由事件循环线程独占；PTY 写由专用写线程独占。核心层因此无需加锁。
5. **配置注入**：配置是显式对象，随装配注入，不使用模块级全局常量。
6. **跨平台一致**：Windows 与 Linux 共用同一套实现，平台差异全部收敛在运行时层；不在上层写平台分支。
7. **不降级、不兼容、不缓解**：存在多方案时选最优，不留兼容层与死代码。

## 3. 分层总览

依赖方向 `A → B` 表示 A 依赖 B：

```
共享底部:   foundation ──→ (标准库)
            protocol   ──→ foundation
守护链:     core ──→ protocol → foundation
            runtime ──→ core → protocol → foundation
            service ──→ runtime → core → protocol → foundation
            transport(server) ──→ service → protocol → foundation
            adapters(server)  ──→ transport(server) → service
客户端链:   transport(client) ──→ protocol → foundation
            adapters(client)  ──→ transport(client) → protocol
```

| 层 | 包 | 职责 | 硬约束 |
|---|---|---|---|
| 基础 | `foundation/` | 日志、错误、编码、字符宽度、平台探测、id/时间戳 | 仅标准库；无领域语义；被 ≥2 层使用 |
| 线协议 | `protocol/` | 帧格式、消息模型、信封、会话消息 schema、转义序列边界扫描、共享向量 | 仅依赖 foundation |
| 核心层 | `core/` | 会话模型、生命周期、日志、视图、对齐纯函数、端口 | 不 import 原生扩展与上层；**只认 uid**；**不含返回条件与等待引擎** |
| 运行时 | `runtime/` | 宿主适配、进程树、平台隔离、单实例 | **唯一**可 import 原生扩展与平台 API |
| 开发接口 | `service/` | 会话目录、等待引擎、订阅编排、会话管理、命令分发、插件、通知、配置 | 传输无关；不 import transport/adapters |
| 外网兼容层 | `transport/` | 线协议编解码、传输、认证 | 不依赖任何适配器 |
| 接入层 | `adapters/` | MCP / CLI / Web 适配器及各自客户端 | 各适配器互不感知 |

**客户端链止于 `protocol`：** 客户端只依赖 `foundation + protocol + 客户端传输`，永不 import `service / runtime / core`。守护进程与客户端之间**唯一的契约就是 `protocol`**，这正是"两端可跨机"的落地方式。上面那条"守护链"描述的是守护进程侧的依赖关系。

**守护进程** = `core + runtime + service + transport(server)` 装配成的单一进程。接入层既可以在守护进程**进程内**挂载（直接调 service），也可以作为**独立客户端进程**经 transport 连入。两种挂载方式对核心层完全透明。

**公共部分**只有 `foundation` 与 `protocol` 两个包。准入门槛三条**同时**满足：仅依赖标准库、无领域语义、被 ≥2 层使用。`protocol` 例外地承载**线协议的消息 schema**（这是它的职责），但不得承载业务实现。

**核心层与命令层的边界**：核心层只持有终端的**状态与语义**——会话、宿主端口、终端模型、字节日志、视图、会话注册表，以及对齐决策的纯函数 `plan_attach`。**核心层不含连接、不含推送、不含订阅者、不含线程、不含返回条件与等待引擎。** 订阅者的持有、订阅生命周期（attach / detach / resync / ack）、按游标补齐推送、以及"等到什么条件再返回"的判定，全部在命令层。这样核心层保持"纯维护终端"，而订阅与条件语义不会泄漏进核心。

**会话身份的两级模型**：核心层只认 `uid`（uuid4，会话在核心层内的唯一标识）；`sid`（用户自定义标识）是命令层的语义，由 service 的**会话目录**持有 `sid ↔ uid` 映射与 `tags` / 会话级配置。前端一律说 `sid`，service 翻译成 `uid` 调用核心层；核心层的事件带 `uid`，service 翻译回 `sid` 再发给前端。**web 与 CLI/MCP 都是 service 的前端**，因此都能看见 `sid`，无需让 web 直接触碰核心层——这就是"统一会话管理层"的落点，**不再新增一层**。

**`example/` 不是接入层的依赖模板**：它是核心层的测试驱动，也是 adapter 的占位——为了在没有命令层的情况下把核心层跑起来，它**直接依赖 `core + runtime`**。真正的接入层（MCP / CLI / Web）依赖链是 `adapters → service → runtime`，**不得照搬 example 直连核心层**，否则会绕开会话目录（`sid`）与等待引擎。

## 4. 核心层 `core/`

> 详细接口设计见 [core设计.md](core设计.md)。

**核心层只做三件事**：Pty 会话核心、子进程会话核心、会话生命周期管理。它维护终端的**状态与语义**，不判定"什么时候该返回"，也不做匹配。

### 4.1 统一会话契约

Pty 会话与子进程会话共享同一套契约，差异只落在"输出视图"与"输入编码"两处。

**共同部分**：

- 身份：`uid`（uuid4，核心层内唯一且不可变）。`sid` 不属于核心层（见第 3 节）。
- 模式：`SessionSpec.mode` 是**开放字符串标签**，由接入方定义；核心层不校验，内置 `pty` / `subprocess` 两种。
- 生命周期：`created → starting → running → exited → closed`，详见 4.3。
- 输出真源：输出字节日志，详见 4.4。
- 输出流：`streams()` 按流读写（Pty 一路、子进程两路）。
- 返回数据：统一的视图查询接口，详见 4.5。
- 状态：`running` / `exit_code` / `start_time` / `error`。

**差异部分**：

| 维度 | Pty 会话 | 子进程会话 |
|---|---|---|
| 输出视图 | 可见屏幕文本 / 全量输出 / 字符格栅 / SVG / 位图 | 仅字节流视图 |
| 输入 | 文本 + 控制字符展开 + 键盘/鼠标编码 | 文本（写 stdin） |
| 尺寸 | `cols` / `rows`，可 resize | 无 |
| 终端模型 | 有（VT 解析） | 无 |
| 流数 | 单一合并流 | stdout / stderr 分离 |

### 4.2 两个会话核心

```
core/
  ports.py           端口定义（依赖倒置接缝）+ 内置模式标签 / Stream
  errors.py          领域错误
  scan.py            转义序列与多字节字符的边界扫描
  journal.py         输出字节日志（真源）+ 对齐纯函数 plan_attach
  views.py           字节视图（全量 / 切片 / 行 / offset / grep）
  session/
    state.py         SessionState / 状态机
    base.py          Session 抽象：身份 + 生命周期 + 摄入 + 视图
    registry.py      会话注册表（uid 主键）
  terminal/          Pty 会话核心（特化）
    session.py       TerminalSession
  process/           子进程会话核心（特化）
    session.py       ProcessSession
```

`Session` 抽象持有共享逻辑（生命周期、日志、摄入、视图），通过端口调用宿主；`TerminalSession` 与 `ProcessSession` 只实现各自的输出流数与模型喂入。

**摄入在核心层闭合**：`Session.ingest_stream(stream, data)` 在内部完成"喂终端模型 + 追加日志"，保证 `fed_offset == journal.end`（重建路径正确性的前提），并返回本次的 offset 区间与模型要回写的应答字节。命令层据此推送、据此把应答交给写线程——核心层不关心谁在订阅。

### 4.3 生命周期管理

```
created ──start()──→ starting ──spawn 成功──→ running
                                    │
running ──子进程退出──→ exited ──close()──→ closed
running ──stop()/kill()──→ exited ──close()──→ closed
starting ──spawn 失败──→ closed（error 记录原因）
```

- **会话是守护进程的一等对象，生命周期与任何连接无关**：attach / detach、客户端断开都不影响会话；子进程退出**不销毁会话**，退出码与日志保留，仍可继续订阅与查询。
- 只有显式 `close`（或守护进程退出）才真正拆除并释放资源。
- 释放时机集中在一个显式的状态机里，不散落到各调用点。
- **"退出"与"排空"是两件事**：`exit_code` 一拿到就记（`stop()` 强杀后也要等它出现，否则 `drained` 永远为假），但"不再会有输出到达"要等所有输出流 EOF（`drained`）。进程退出与尾部输出到达之间有竞态，把两者混为一谈会丢掉最后一段输出。EOF 由驱动方（读线程 / 泵）在排空后打标记——**EOF 不等于退出**，程序可以先关掉 stdout/stderr 而继续运行。

### 4.4 输出字节日志（真源）

会话产出的原始字节按到达顺序追加到日志，构成唯一真源。

- **offset 从 0 起、单调递增、永不回退**；区间语义统一为半开 `[start, end)`。
- 日志有内存预算，超预算时从头裁剪；**裁剪点必须对齐转义序列边界**（否则重放会从序列中间切断，产生可见乱码）。
- 客户端游标若落后到已裁剪区间，服务端发显式 `behind` 要求重同步，不静默丢弃。
- **热状态**（屏幕内容、光标、SGR）与**冷状态**（备用屏、字符集、tab stops、键盘栈）都由字节流决定，因此新客户端整段重放 `[0, end)` 即可还原到与"从头就在的客户端"逐字节相同的状态，无需逐个状态保存与恢复。

### 4.5 返回数据（派生视图）

所有返回数据都是从真源派生的视图，按需生成、不额外维护状态。

**字节视图**（直接切片日志，每流独立）：

- 字节流全量
- 最后 N 行 / 指定行范围
- 最后 N 字节 / 指定字节范围
- offset 增量（自上次游标起的增量）
- 正则匹配（原始字节）

**屏幕视图**（Pty 会话，经终端模型渲染）：

- 可见屏幕纯文本（`screen_text`）
- 全量输出：含滚动历史的可见文本（`full_text`）
- 可见屏幕的字符格栅（`screen_cells`，宽字符的续格为空串）
- 屏幕 SVG / 位图（`render_svg` / `render_image`，可见区）

屏幕视图只在 Pty 会话存在；终端模型由事件循环线程独占，喂入的字节与日志同源（见 4.7 的不变量）。

**"全量输出"只有一个含义**：含滚动历史的所有可见文本；字节侧的对应物叫**字节流全量**。由这些原料在上层派生的返回数据（屏幕 diff、可见屏幕第 N 列）与判定（回显抑制）都在命令层——核心层只出原料。`rebuild_bytes()` 不在返回数据之列，它是订阅者重同步用的重建字节（见 4.6）。

### 4.6 订阅与同步

订阅的**编排**在命令层（订阅者对象、游标、出站队列都在那里）；核心层只提供两样东西：字节日志本身，以及一个**纯函数** `plan_attach(cursor) → Resume | Rebuild`（对齐决策依赖日志的裁剪边界与转义序列语义，因此贴着日志放）。

- 每个订阅者持有 `next_offset`（它下一个需要收到的字节偏移）。有新输出时，服务端从其游标补齐到日志末尾，补到哪推进到哪。
- **拥塞只让推送暂停，绝不丢字节**：没推的部分留在日志里，队列排空后从游标继续。
- 慢订阅者的两种回程信号各管一道闸：传输层排空解除**发送队列水位**；客户端 `ack(offset)` 解除**解析窗口**（最多推送到 `acked + window`）。
- 新订阅者视作游标 0；若 0 已落到已裁剪区间（`start_offset > 0`），与落后游标一样走重建字节（`rebuild_bytes()`）重同步——**这是整套机制里唯一有损的路径**。

### 4.7 端口定义（依赖倒置）

核心层定义它需要宿主提供什么，运行时层提供实现：

```
# 共同生命周期
HostLifecycle:  read(max_bytes, timeout) / write(data) / try_wait() / kill() / close()
                pid

# 终端宿主（Pty）
TerminalHost:   ingest(data) -> response_bytes     # 喂终端模型，返回要回写应用的应答
                resize(cols, rows) / metadata()
                rebuild_bytes()                    # 重建字节（重同步用），不是屏幕内容
                screen_text() / full_text()        # 可见屏幕 / 全量输出（可见文本）
                screen_cells()                     # 字符格栅（宽字符续格为空串）
                render_svg() / render_image(scale, fmt)   # 屏幕视图（可见区）

# 子进程宿主
ProcessHost:    read_stderr(max_bytes, timeout) / close_stdin()
```

**线程归属是端口契约的一部分**（方法按允许调用的线程划分，而不是按功能划分）：

| 方法 | 唯一允许的调用者 |
|---|---|
| `read` / `read_stderr` | 读线程 |
| `ingest` / 屏幕视图读取 / `resize` / `refresh` | 事件循环线程 |
| `write` | 写线程 |

由此得到两条可断言的不变量：`ingest()` 与日志追加在同一线程**相邻执行**，故 `fed_offset == journal.end`；因此读取屏幕（`screen_text()` / `rebuild_bytes()` 等）期间不可能有 `ingest()` 插入，读到的恰是"重放 `[0, end)` 之后"的状态。

## 5. 运行时层 `runtime/`

**唯一可以 import 原生扩展（`pywezterm` 等）与平台 API 的层。**

```
runtime/
  vendor.py           把不安装的长期依赖接进 sys.path（在任何 import 之前完成）
  pty_host.py         pywezterm 宿主：PTY + 终端模型（惰性导入，纯子进程场景不碰）
  subprocess_host.py  子进程宿主：Popen 双管道
  host_factory.py     按模式标签选宿主 + 启动期依赖检查
  process_tree.py     进程树强杀（Windows Job Object KILL_ON_JOB_CLOSE / Linux 进程组）
  bridge.py           读线程 → 所有者线程的有界桥（背压落点）
  reader.py           每路输出一个读线程
  runner.py           会话运行时驱动：读线程 + 写线程 + 所有者侧 pump()
  platform/           平台隔离：single_instance.py（单实例锁）/ signals.py
```

- **终端宿主**：`pywezterm.Pty`（PTY）+ `pywezterm.Terminal`（wezterm-term 终端模型）。PTY 读与模型喂入分离到不同线程（见 4.7）；PTY 写在放掉 GIL 后做阻塞写。
- **子进程宿主**：`Popen` 双管道，`start_new_session` / `CREATE_NEW_PROCESS_GROUP` 让子进程自成进程组。读用**带超时**的方式而不是纯阻塞（PTY 在子进程退出后不返回 EOF，纯阻塞会永久挂住线程）。
- **进程树**：Windows 把子进程加入 Job Object 并设 `KILL_ON_JOB_CLOSE`——句柄一关（进程死），作业内残余进程由内核收掉；Linux 让子进程自成进程组（`start_new_session`），强杀时按组发信号。
- **命令归一化**：工厂入口统一把命令归一为 `argv` 列表，后端只消费列表。

## 6. 开发接口层 `service/`

**传输无关的用例编排层。** 接入层无论走进程内还是经 transport，最终都调用这里的用例。**返回条件与等待引擎属于这一层**，不在核心层。

```
service/
  directory.py        会话目录：sid ↔ uid 映射 + tags / 会话级配置
  sessions.py         SessionManager：创建 / 查询 / 列表 / 关闭；全局默认值与会话值
  conditions.py       返回条件词汇与匹配器
  wait.py             等待引擎：把返回条件喂给会话输出，判定何时返回
  subscriptions.py    订阅者与订阅编排（游标 / ack / 出站队列 / 补齐推送）
  dispatcher.py       命令分发：把统一命令映射到用例，解析返回条件为 WaitSpec
  plugins/            插件系统（宿主 + 注册表 + 钩子引擎 + 清单校验）
  notify.py           通知：异步返回结果的存储与取回
  config.py           配置对象与默认值解析
```

### 6.1 等待引擎

"等到什么时候返回"统一为一组条件词汇，由**命令层的等待引擎**求值。

| 条件 | 语义 | 适用 |
|---|---|---|
| `notify` | **正交模式**：立即返回，其余条件挂后台继续检查，命中后推送事件 | 全部 |
| `matched` | 正则命中 | 全部 |
| `ended` | 程序退出 | 全部 |
| `crashed` | 程序异常退出 | 全部 |
| `timeout` | 显式超时（兜底） | 全部 |
| `idle` | 静默超时（兜底）：Pty 看**可见文本**是否变化，子进程看**字节流**是否静默 | 全部 |
| `gui` | 检测到 GUI 窗口（异常） | 全部 |
| `echo` | 屏幕/字节流回响命中，用于精确判定命令结束 | 全部 |
| `cancelled` | 被显式取消 | 全部 |

- **`notify` 不是与其它条件并列的选项，而是可叠加的模式**：`notify` + 其它条件 = 立即返回 + 后台继续检查 + 命中后推送事件。
- 求值优先级固定：`cancelled → matched → crashed / ended → idle → timeout`。`matched` 排在退出之前是刻意的：trigger 是用户的显式诉求，一旦出现就定案；`ended` / `crashed` 是兜底。
- **结束以核心层的 `drained` 为准**：进程退出与尾部输出到达之间有竞态，必须等核心层把"退出 + 全部流 EOF"合起来判定，否则会丢掉最后一段输出。
- **等待装载之前到达的输出不能丢**：装载时先用会话已积累的输出试一次匹配——短命令（"打印标记后立刻退出"）的输出与退出都可能发生在装载之前。
- **回显抑制**：正则匹配必须区分"程序回显的输入"与"程序真正的输出"，利用两者在字节结构上的差异（回显是原样字符，输出是转义后的真实字节）做判定。
- 子进程会话启用 `matched` / `ended` / `crashed` / `timeout` / `idle` / `gui` / `notify`；屏幕相关的条件（`echo`）不适用。

**引擎位置**：引擎在命令层，但**判定所需的原料全部来自核心层**——输出由命令层驱动读入（`read_stream`）后转交核心层记账（`ingest_stream`），退出与排空由核心层判定（`exit_code` / `drained`）。因此命令层不需要反向拉取数据流，也不需要在别的线程读终端模型：它就在那个已经拿着字节的驱动循环里做匹配。

### 6.2 其余组件

- **会话目录**：持有 `sid ↔ uid` 映射与会话元数据（tags / 标签 / 会话级配置）。前端用 `sid`，目录翻译成 `uid` 交给核心层；核心层的事件按 `uid` 回来，目录翻译回 `sid`。**这是"统一会话管理层"的落点**——web 与命令层都通过它拿到一致的会话身份，因此不新增一层。
- **订阅编排**：持有订阅者对象（游标 / ack / 出站队列），处理订阅生命周期（attach / detach / resync / ack），有新输出时用核心层的 `plan_attach` 与日志读取，把增量按游标推给各订阅者。**订阅语义不在核心层**——核心层只给日志与对齐纯函数。
- **SessionManager**：会话 CRUD（经会话目录解析 sid）、`stop_all`、全局默认值与会话级值的设置与列举。
- **命令分发**：把"创建终端 / 创建子进程 / 输入 / 读取 / resize / 关闭 / 工作流 / 配置 / 通知"等统一命令路由到对应用例；同时是**认证之后**的统一入口，传输层与进程内调用共用。它**声明**每个命令支持哪些返回条件，把客户端参数**解析**为条件对象（`WaitSpec`）并交给等待引擎。
- **插件系统**：能力由清单声明（触发器 / 消息类型 / 权限 / 配置默认值 / CLI 选项 / 自定义返回条件），代码只实现钩子。插件声明在**命令分发层**，客户端（CLI / MCP）可以接收该层声明的插件能力并据此呈现。插件异常一律隔离，不中断主流程。
- **通知**：异步返回（`notify` 条件）的后端存储。后台把"命令原本的返回"发布到通知队列，`wait` 消费摘要、`notice` 查询完整内容（只读不消费）。

## 7. 外网兼容层 `transport/`

**让核心能力可以被进程外访问的层，覆盖同机与跨机两种形态。**

```
transport/
  protocol/           线协议：帧格式、消息模型、转义序列边界扫描、共享测试向量
  codec.py            编解码
  server.py           监听、连接编排
  transports/         传输：tcp（同机 loopback / 跨机）、tls 包装
  auth/               认证：token（HMAC）/ pubkey（Ed25519）/ TLS 证书
```

### 7.1 传输

传输实现**只有一份 TCP**，跨平台一致；"同机 / 跨机"由**监听地址**与**是否套 TLS**决定：

| 形态 | 监听地址 | 加密 | 认证 |
|---|---|---|---|
| 同机 | `127.0.0.1`（loopback） | 明文 | 默认无 token；可配 token + HMAC |
| 跨机 | 可配置接口 | **TLS**（自签证书 + TOFU） | 可选叠加 token + HMAC |

- **同机走 loopback TCP**：与跨机共用同一份传输实现，零额外依赖，天然跨平台（`AF_UNIX` 在 Windows 的 CPython 上不可用，命名管道需额外依赖且是另一套实现，均不采用）。loopback 监听不触发防火墙、外部不可达。
- **跨机走 TLS**：在 TCP 之上套 TLS，自签证书 + TOFU（首次信任，类似 known_hosts）。TLS 是传输的**包装**，不是独立实现。
- **认证与传输解耦**：认证在信封层面完成，与传输形态无关。

### 7.2 线协议信封

信封是两端共享的统一格式，字段：

```
proto    协议版本（破坏性变更时递增 + 协商）
dir      request | response
type     命令类型
mid      消息 id（请求 / 响应关联）
ts       时间戳（防重放窗口）
kind     呈现意图（表示层据此选渲染通道）
auth     认证凭证 / 签名
payload  业务载荷（分组：op / condition / output / io）
```

- 载荷分组让"操作 / 返回条件 / 返回过滤 / IO"各归其位，内部业务层再拍平成扁平结构消费。
- **会话消息 schema 也定义在 `protocol`**（会话信息、状态、事件等线格式）。web 的 WS 帧与 transport 的 TCP 帧承载**同一份信封与同一批消息类型**，因此"web 与命令层消息一致"是构造出来的，而不是两层各自维护。
- 协议事实来源是**前后端共享的测试向量文件**，两侧各跑一遍。

### 7.3 认证

- `token`：token + HMAC 双向签名；token 可配置，未配置即明文（仅适用于同机）。
- `pubkey` / `tls`：Ed25519 请求签名 + 自签证书 TOFU。

## 8. 接入层 `adapters/`

每个接入形态是一个独立适配器，**互不感知**；客户端是薄壳，只做协议转换与呈现。

```
adapters/
  mcp/        MCP 服务器：把统一命令暴露为标准工具（默认注册基础工具的完整 schema）
  cli/        CLI：命令解析 → 统一命令 → 呈现
  web/        Web：HTTP / WebSocket 网关 + 前端静态托管
```

- **MCP 层**：默认注册基础工具的完整 schema；工具名与统一命令一一对应（见第 9 节）。
- **CLI 层**：解析命令行 → 构造统一命令 → 呈现结果（内容 → stdout，元信息 → stderr）。**创建终端时绝不继承客户端的环境变量**（客户端可能与守护进程不在同一台机器），环境变量必须显式传入。
- **Web 层**：见 8.1。

### 8.1 Web 接入

**web 层不直接触碰核心层。** 它与 `transport` 平级，都是 `service` 的前端——浏览器就是一个客户端，只是走 WS 而不是 TCP/TLS：

```
浏览器 ──WS──▶ web 适配器 ──▶ service（Hub）──▶ core / runtime
                     ▲                              │
                     └──────── outbox 字节流 ◀───────┘
```

- **浏览器说的也是 `sid`**：与 CLI / MCP 完全同构，经 service 的会话目录翻译成 `uid`。因此 web 能看见 `sid`，而核心层始终只见 `uid`。
- **一条连接两个任务，职责严格分开**：**接收循环**（WS 文本帧 → 解析成命令 → 命令分发；WS 二进制帧 → 输入字节 → 会话）与**发送循环**（排空该订阅者的出站队列 → 写 socket）。分开不是风格而是**正确性**要求：命令层的所有决策（订阅、补流、对齐点登记）必须在一个**没有 await 的临界区**里原子完成；若命令层自己 `await send`，一个慢客户端就会拖住整条广播路径，状态机中间也会出现 await 点。
- **发送循环不解析任何东西**，只搬运字节；**接收循环只发两类东西**：帧错位与输入越限的致命错误（走关闭帧，不走出站队列，否则错误会排在断开之后）。
- **控制消息与字节流分帧**：控制消息走文本帧、终端字节流走二进制帧（WS 原生两种形态，不自己多路复用）；相邻的二进制段合并成一次发送，避免一帧一个 syscall。
- **握手必须校验 `Host` / `Origin`**：浏览器**不会**对 WebSocket 施加 CORS 保护，恶意网页可以对 `127.0.0.1` 发起 WS 连接（DNS rebinding / 本地服务扫描），校验 Origin 是这里唯一的防线。
- **断开连接 = 只解除订阅**，绝不销毁会话。
- **只有这一层可以 import web 框架**（AST 测试强制）。前端由后端同源托管，消除 CORS 与代理。

## 10. 线程模型

**所有会话状态（含终端模型与日志）只在事件循环线程上改动；PTY 写只在写线程上发生。** 并发正确性靠"单线程所有者 + 唯一写者"，而不是加锁。

```
读线程 ──有界桥──→ 事件循环 ──出站队列──→ 发送循环 ──→ socket
   ↑                  ↑
host.read()      Session.ingest_stream()（喂模型 + 追加日志，相邻、同一线程）
                      ↓
                 写线程 ──→ PTY（客户端输入 + 宿主应答，唯一写者）
```

线程账（每个会话）：

| 会话类型 | 专用线程 | 说明 |
|---|---|---|
| Pty | 2（读 1 + 写 1） | `Pty.read` / `Pty.write` 都是阻塞调用；且 `Pty` 未暴露 `fileno()`，Python 侧无法多路复用 |
| 子进程 | 3（stdout 读 + stderr 读 + 写 1） | 两路管道各一个读线程；写线程是唯一写者 |

所有者循环是**共享**的（不是每会话一个），默认 1 个，可横向分片（把一批会话挂到多个所有者循环上）。

- 写 PTY 单独一个线程：写是阻塞操作，不能压在事件循环上。
- 读桥有界：队列满时读线程等待，背压向 PTY 传导（进而让子进程写阻塞）。
- 宿主应答（DSR / 焦点应答等）必须无条件入队，否则模型永远收不到回复而卡死。
- **读与写不能合成一个线程**：子进程写满输出管道被阻塞时，若同时在阻塞写它的输入管道，双方互相等待，会死锁。

## 11. 负载与背压

三个方向各有一道闸，互不替代：

1. **生产端（子进程吐得快）**：有界桥 + PTY 自身读缓冲水位。桥满 → 读线程等待 → 停止从 PTY 读 → 管道填满 → **子进程写阻塞**。背压最终落到子进程，服务端不无限缓冲。
2. **消费端（客户端跟不上）**：每客户端游标 + 出站队列水位 + 解析窗口（`acked + window`）。**拥塞只让推送暂停，绝不丢字节**；游标落后到裁剪点 → 显式 `behind` → 快照重建。
3. **公平性（一个会话饿死其他）**：所有者循环每轮**按预算处理**（每会话每轮最多 N 字节 / M 个块），不把某个会话的积压一次倒完。

内存闸：字节日志按预算裁剪，裁剪点对齐转义边界。

**卡住的两种情形**：

- **子进程不读 stdin**（写阻塞）：写线程独立，循环不受影响；写队列按字节计量，超高水位给该客户端下发 `InputHold`（发送方本端排队），超硬上限 = 违约 → 显式断开。**绝不用"停止读 socket"做背压**——那会把同一条连接上的控制面（关会话、取消）一起堵死。
- **子进程卡死**（要强杀）：`stop()` **先强杀进程树**（Windows Job Object / Linux 进程组），再关宿主——Windows 上 `host.close()` 可能要等控制台客户端退出（可达数百秒且持着 GIL）。**资源释放两阶段**：同步摘除（会话立刻从列表消失、不再扇出）+ 线程里释放（阻塞多久都不挡循环）。

**TUI 巨量输出**：除上述三闸外，订阅要能声明**订阅模式**——`raw`（原始字节流，客户端自己重渲染）或 `screen`（服务端渲染好的快照 / diff）。TUI 满屏重绘时，`screen` 模式的传输量比 `raw` 低几个数量级。

## 12. 单实例与守护进程生命周期

### 12.1 单实例

守护进程**强制单实例**。理由是硬的：会话坐标（offset、日志、订阅表）活在单进程内存里，两个守护进程会各自维护互斥的 offset；监听端口也会冲突。

- **Windows**：命名互斥体（`CreateMutexW`），内核对象，进程退出自动释放。
- **Linux**：`flock` 锁文件（或抽象 `AF_UNIX` 占位）。
- 实现位置：`runtime/platform/single_instance.py`（唯一碰 OS 的层）。
- 锁名带命名空间（默认按用户 + 配置名），让多用户与测试可共存；**不提供关闭单实例的开关**。
- 锁随进程退出由内核释放，因此**不需要额外的 stale 锁检测**。

### 12.2 启动（严格有序，失败逆序回滚）

1. 解析配置：命令行 > 环境变量 > 配置文件 > 默认值；命令行**只覆盖显式给出的项**，不把默认值误当用户意图压掉环境变量。
2. 取单实例锁（最早取，避免两个进程同时初始化）。
3. 依赖检查：原生扩展能否导入。不能 → **拒绝启动**（退出码 2），日志说明怎么补——绝不"起来了却建不出会话"。
4. 准备数据目录与日志（日志目录、运行时目录：pid / 锁 / 临时文件）。
5. 装配：`core`（会话注册表）→ `runtime`（宿主工厂）→ `service`（目录 / 等待引擎 / 订阅 / 分发）→ `transport`（监听器）。**装配顺序即依赖顺序**。
6. 绑定监听器（loopback / TLS）；任一失败 → 关闭已绑定的，退出。
7. 写 pid、通知就绪。
8. 装信号处理。
9. 进事件循环。

每一步都必须能回滚：已绑的监听要关、已起的线程要停、锁要放。

### 12.3 运行

- 事件循环驱动：读桥 → `ingest_stream` → 推送；命令层的等待引擎按条件求值；信号。
- **会话生命周期与守护进程解耦**：客户端 attach / detach、子进程退出，都不销毁会话。
- 可观测：`get_daemon_status`（pid、启动时长、会话数、监听地址、配置摘要）与日志轮转。
- **不做配置热重载**：配置在装配时注入，改配置必须重启，避免"一半新配置一半旧配置"的中间态；会话级配置可运行期改。

### 12.4 停止（逆序 + 整体超时兜底）

触发：显式 `stop` / `SIGTERM` / `SIGINT` / 致命错误。

1. 关监听器：不再接新连接。
2. 置 `draining`：不再接新命令，在途命令允许完成。
3. **会话收尾**：对每个会话**先强杀进程树，再关宿主**。宿主关闭可能无界阻塞（部分平台上可达数百秒且持着 GIL），因此每个会话带超时、放在线程里做。
4. 停读 / 写线程与有界桥。
5. 刷日志、释放锁、删 pid。
6. **整体超时兜底**：到点强制退出并在日志留痕——没有这条，一个卡住的宿主关闭会让停止流程永不返回。

### 12.5 崩溃（内核兜底，不留孤儿）

守护进程异常死亡时，会话必须一起收尾，否则会留下占着 PTY 的孤儿进程。

- **Windows**：Job Object 设 `KILL_ON_JOB_CLOSE`——作业句柄一关（进程死），作业内所有进程被内核杀掉。
- **Linux**：进程组 + 父进程退出兜底。

正常退出走优雅收尾，异常崩溃由内核兜底。**两条路都要有**。

### 12.6 崩溃后重启

- **会话不可恢复**：offset、字节日志、终端模型全在内存里。重启后客户端拿到"会话不存在"，不假装恢复。
- 数据目录只持久化配置、密钥、日志；**不持久化会话状态**。
- 单实例锁随进程退出释放，因此重启不需要处理 stale 锁。

### 12.7 谁守护谁

守护进程**不自守护**（不自重启）。`start` 负责 spawn 与就绪探测（连 loopback 探活），也可交给系统服务管理器。崩溃时子进程由内核兜底收掉，会话状态丢失，客户端重连重建。

**两种"断开"含义不同**：客户端断开只解除订阅，会话照常活着；守护进程退出则必须让会话一起收尾。

## 13. 目录结构

```
src/agentic_tty/
  foundation/   基础设施：日志、错误、编码、字符宽度、平台探测、id
  protocol/     线协议：帧、消息模型、信封、会话消息 schema、转义边界扫描、共享向量
  core/         核心层：会话模型、生命周期、日志、视图、对齐纯函数、端口
  runtime/      运行时层：宿主适配、进程树、平台隔离、单实例、依赖接入
  service/      开发接口：会话目录、等待引擎、订阅编排、会话管理、命令分发、插件、通知、配置
  transport/    外网兼容层：编解码、传输、认证
  adapters/     接入层：mcp / cli / web
  daemon/       守护进程装配与入口
  example/      示例层：adapter 的占位，也是核心层的测试驱动（假宿主 / 程序库 / CLI / Tk 管理台）
                直接依赖 core + runtime、不经 service，不可作为接入层的依赖模板（见第 3 节）
vendor/         长期依赖（原生扩展），不 pip 安装，由 runtime 接入 sys.path
tests/          单测 / 契约测试 / 接入测试（与 src 镜像）
```

## 14. 依赖强制与测试

- **分层测试**：`tests/test_layering.py` 扫 AST 强制依赖方向；`core` 不得 import 原生扩展与上层包，`runtime` 之外不得 import 原生扩展，`adapters` 之间不得互相 import，客户端链不得 import `service / runtime / core`，web 框架只允许出现在 `adapters/web`。
- **单测**：全部跑在假宿主（fake host）上，无需原生扩展与网络；假宿主的线程归属与真实宿主一致，因此订阅、补齐、裁剪、重同步、流控、条件判定都能被确定性测出。
- **契约测试**：接上真实 PTY + 终端模型后仍成立（进程启动 / 控制台附着 / 进程退出等真实操作系统事件）。
- **接入测试**：MCP / CLI / Web 各自的端到端。
- **测试同步纪律**：不用固定睡眠等异步效果，用具名栅栏等待可观察条件；由测试机器化执行。

## 15. 实施顺序

1. `foundation` + `protocol` + `core`（会话模型、日志、视图、生命周期）+ 假宿主：核心逻辑全绿。
2. `runtime`：pywezterm 终端宿主 + 子进程宿主 + 进程树 + 单实例；契约测试通过。
3. `service`：会话目录、等待引擎、订阅编排、会话管理、命令分发、通知、配置。
4. `transport`：线协议 + loopback TCP + token 认证；守护进程可被进程外访问。
5. `adapters/cli`：最小可用 CLI，端到端跑通"起会话 → 输入 → 等待 → 读屏"。
6. `transport` 增加 TLS + pubkey 认证：支持跨机。
7. `adapters/mcp`：暴露完整工具集。
8. `adapters/web` + 插件系统 + 工作流编排。
