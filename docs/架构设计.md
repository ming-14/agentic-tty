# agentic-tty 架构设计

## 1. 定位

一个以**伪终端（PTY）会话**与**子进程会话**为核心能力的守护进程，让调用方（AI Agent、脚本、人类）能像真人一样驱动交互式程序：起会话、发按键、等提示符、读屏幕。

- 跨平台：Windows（ConPTY）/ Linux（openpty）
- 会话形态：`pty` 与 `localpty`（都是终端屏幕语义，区别只在宿主）／ `subprocess`（字节流语义）
- 多接入：多条独立的消费者链路（命令处理层 / web / MCP / CLI / 桌面验证台），可分布在同一台机器的不同进程，也可跨机
- 单一真源：会话输出以原始字节流为准，屏幕等皆为派生视图

## 2. 设计原则

1. **层与层之间是接口关系**：一个层对外只提供接口；**层的下游没有某个必须的消费者**——任何一层都可以被删掉而不影响别的层。
2. **被依赖的一方绝不依赖依赖它的一方**：依赖只能从消费者流向被消费者，反向一律禁止。
3. **公共层只提供契约，不承载业务**：任何层都可以导入它，它不导入任何非公共层。
4. **单一真源**：会话输出以输出字节日志为唯一真源，其余查询皆为派生视图。
5. **单线程所有者 / 单一写者**：终端模型与日志由事件循环线程独占；PTY 写由专用写线程独占。核心层因此无需加锁。
6. **配置注入**：配置是显式对象，随装配注入，不使用模块级全局常量。
7. **跨平台一致**：Windows 与 Linux 共用同一套实现，平台差异全部收敛在宿主实现与传输实现里；不在上层写平台分支。
8. **不降级、不兼容、不缓解**：存在多方案时选最优，不留兼容层与死代码。

## 3. 分层总览

### 3.1 核心层（能力体）

**核心层不是一个包，是一个"能力体"**——由两个包合成，跑在**一个进程**里：

```
┌──────────────────── 核心层（能力体）────────────────────┐
│  core/          会话核心与语义 + 宿主实现（core/runtime）  │
│  daemon/        进程装配与生命周期（单实例、信号、启动与收尾）│
│  ────────────────────────────────────────────────────  │
│  对外只提供四件事：                                       │
│    ① 生命周期管理（守护进程自身 ＋ 会话）                   │
│    ② 运行程序的能力（终端会话 / 子进程会话）                 │
│    ③ 会话数据的订阅（游标 ＋ 唤醒；不认识订阅者）             │
│    ④ 一个本机接入点 —— **不是网络**，只是本机 IPC             │
└───────────────────────────────────────────────────────┘
```

- `core/` 顶层是**会话模型与端口**（抽象接口），`core/runtime/` 是**宿主实现**（真 PTY / 真子进程 / 进程树）。core 直接耦合 `core.runtime`，因此默认宿主工厂由 core 自带，不必由外部装配层注入。
- `core/runtime/` 与假宿主（测试替身）处于**同一个生态位**——两者接的是同一组上游端口，除此之外互不相干。假宿主经 `SessionRegistry(host_factory=...)` 注入，**这是保留的扩展点**。
- `daemon/` 就是**那个进程**：管**生命周期**、**承载**与**转发**——做唯一的所有者线程、把接入点上的请求交给请求处理层。它自带**装配层**与**默认请求处理层**（这两样必须 import core，否则装不进 core），与 `core` 自带 `core.runtime` 是同一手法：**默认实现自带，注入点（`handler_factory=`）保留**。它也可以 import `protocol` / `transport`：接入点（`pipe://`）是它的活。
- **"不 import core" 是给 `daemon/` 里"机制"那几份的**（`server.py` / `access_point.py` / `handler.py` / `platform/` / `errors.py`）——机制必须与 core 无关，换掉请求处理层机制一行不改。**只有 `kernel.py` / `assembly.py` / `__main__.py` 三个文件可以 import core**；这条由 AST 断言按**文件**强制（见 §14）。

**核心层不实现网络**：它不开监听端口、不碰 TCP、不认识任何线协议。它对外唯一的通道是那个**本机接入点**（命名管道 / `AF_UNIX`），供同一台机器上的消费者进程连进来——这个口子由 `daemon/` 直接持有（`transport.listen("pipe://…")`），搬的是本机字节，不是网络。

### 3.2 消费者：连到某一层，各自对外提供自己的 API

**消费者既不是"核心层的一部分"，也不是彼此的一部分。** 每一个消费者都：

- **直接连到它消费的那一层**（核心层，或者别的消费者）；
- **自己对外提供自己的 API**（自己开服务器，或只开一个窗口）；
- 与其他消费者**毫无关系**——**一个消费者不得 import 另一个消费者**。

```
                              一台机器
 ┌─ 守护进程（一个进程）───────────────────────────────────────────────┐
 │   core（含 core/runtime）＋ daemon                                 │
 │   对外：① 生命周期管理 ② 运行程序的能力 ③ 本机接入点（不是网络）        │
 └──────────────────────────────┬────────────────────────────────────┘
                                │ 连接（本机管道）
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
  客户端命令处理层             web 层                 daemon_test
  （自开服务器）             （自开 HTTP/WS）          （不开网络，开窗口）
        │  ▲
        │  └─── mcp 层 / CLI 层
        │        （必须经过本层，禁止跨层引用）
        │              │
  客户端 cli        客户端 mcp
```

- **只有 web 层直接连核心层**，由它自己开服务器服务网页端。
- **mcp 层与 CLI 层不得直接连核心层，必须经过客户端命令处理层**——禁止跨层引用，只能找相邻层。
- **客户端侧（客户端 cli / 客户端 mcp / 网页端）与消费者之间是"连接"，不是 import**：消费者负责开服务器，客户端只是连上去。项目作为某一端的客户端时，**绝不 import 服务端任何一层**。
- 「直接连」指的是**直接连到那一层所在的那个进程**，不经别的消费者；**它不等于"同进程"**——消费者可以是完全独立的进程。

### 3.3 公共层：契约，不是业务

`foundation` / `config` / `protocol` / `transport` 四个包是**公共层**：任何层都可以导入它们，**它们不导入任何非公共层**。

| 包 | 提供什么 |
|---|---|
| `foundation` | 日志、错误基类、id / 时间戳、平台原语（实例互斥） —— 无领域语义的基础件 |
| `config` | **配置常量**：名字前缀 / 默认实例名 ＋ 由它们派生的本机实例命名（运行时目录 / 端点名 / 锁名）＋ 各层的配置对象 —— **配置就住在这个包里，写死，没有别的地方可配** |
| `protocol` | 通用底座（帧、信封、响应约定、增量读帧器）＋ **按边界分区的线契约**（`contracts/`）—— **两端之间唯一的契约** |
| `transport` | 字节流抽象、地址 scheme 分派 —— **只搬字节，两侧共用同一份实现** |

**准入门槛**三条**同时**满足才可放入：仅依赖标准库、无领域语义、被 ≥2 层使用。

- `protocol` 例外地承载**线协议的消息 schema**（这是它的职责），但不得承载业务实现。**消息 schema 按边界分区**：一条我们自己的跨进程边界一份——`contracts/daemon_ipc.py`（守护进程 ↔ 下游消费者，载 `uid`）、`contracts/consumer_ipc.py`（下游消费者 ↔ 它的客户端，载 `sid`）。**分区之间零依赖、互不共享类型**，改一条边界不波及另一条。外部协议（MCP / CLI / HTTP）是别人定的，**不进公共层**。
- **转义序列边界扫描不在此列**——它服务于终端字节日志的裁剪对齐（见 4.4），是终端语义，因此归 `core/scan.py`。
- 公共层可选（"把都有的封装起来"），但**不可滥用**：多一个公共层成员，就多一份所有层都要跟着走的契约。

**公共层内部只剩一条链**：`protocol → foundation`。`config` 只压在 `foundation` 上；`transport` 与 `protocol` **彼此独立**——两者都只压在 `foundation` 上，谁也不认识谁；把帧与字节流缝起来的是装配方注入的那一个函数，不是某一层的依赖。

**`transport` 不认识命名习惯**：管道名是**完整名字**（`config.constants.endpoint_name()` 加前缀），地址**必须带运行时目录**——它不猜任何平台默认值（猜错不如报错）。

### 3.4 依赖方向与硬约束

| 包 | 允许依赖 |
|---|---|
| `foundation` | foundation |
| `protocol` | foundation, protocol |
| `core` | foundation, core |
| `transport` | foundation, transport |
| `daemon` | foundation, protocol, transport, core, daemon |
| 各消费者 | 各自的依赖面（见 3.2），彼此零交集 |

- **原生扩展只允许落在各自的宿主格子里**（`pywezterm` → `core/runtime/pywezterm_pty/`、`resvg_py` → `core/runtime/local_pty/`）；`core/` 的其余部分与任何上层都不得 import 它们。唯一的例外是验证台 `example/ui`——Tk 的 `PhotoImage` 没有 SVG 解码器，它自己用 `resvg_py` 栅格化。
- **`daemon/` 的"机制"不许 import `core`**（`server.py` / `access_point.py` / `handler.py` / `platform/` / `errors.py`），只有 `kernel.py` / `assembly.py` / `__main__.py` 可以——白名单由 AST 断言**按文件**强制。它**可以 import `protocol` / `transport`**（只用 `transport` 的本机管道部分）；但**接缝上的报文对它仍不透明**（它只解出帧，不解释语义）。
- **客户端链只依赖公共层**（`foundation + config + protocol + transport`），永不 import 核心层或消费者。
- **守护进程只由它自己支配**：启动、配置、收尾都在 `daemon/` 的入口里。**消费者格——包括验证台——不得启动它**：它们只被**告知**要连哪个名字（管道名），然后自己算地址去连；**不拉子进程、不给它传参、不替它决定叫什么**。名字是两端各算一次的约定，不是某一方的私产。
- 以上全部由 AST 扫描测试强制，不靠自觉（见第 14 节）。

## 4. 核心层 `core/`

**核心层只做三件事**：Pty 会话核心、子进程会话核心、会话生命周期管理。它维护终端的**状态与语义**，不判定"什么时候该返回"，也不做匹配。

它对外提供**数据接口**（视图与字节切片）与**订阅机制**（游标 ＋ 唤醒，见 4.6）——但**不认识订阅者**：谁在听、怎么发，都是消费者的事。

### 4.1 统一会话契约

Pty 会话与子进程会话共享同一套契约，差异只落在"输出视图"与"输入编码"两处。

**共同部分**：

- 身份：`uid`（uuid4，核心层内唯一且不可变）。`sid` 不属于核心层——那是消费者的语义。
- 模式：`SessionSpec.mode` 是**开放字符串标签**，由接入方定义；核心层不校验，内置 `pty` / `subprocess` / `localpty` 三种。`pty` 与 `localpty` 共用 `TerminalSession`，差别只在宿主（`pty` = pywezterm 一体；`localpty` = 平台原语 + pyte）。
- 生命周期：`created → starting → running → exited → closed`，详见 4.3。
- 输出真源：输出字节日志，详见 4.4。
- 输出流：`streams()` 按流读写（Pty 一路、子进程两路）。
- 返回数据：统一的视图查询接口，详见 4.5。
- 状态：`running` / `exit_code` / `start_time` / `error`。

**差异部分**：

| 维度 | Pty 会话 | 子进程会话 |
|---|---|---|
| 输出视图 | 可见屏幕文本 / 全量输出 / 字符格栅 / SVG / 位图 | 仅字节流视图 |
| 输入 | 文本 + 控制字符展开 + 键盘/鼠标编码 | 文本（写 stdin） |
| 尺寸 | `cols` / `rows`，可 resize | 无 |
| 终端模型 | 有（VT 解析） | 无 |
| 流数 | 单一合并流 | stdout / stderr 分离 |

**PTY 的"回车"是 CR（0x0D）**：Pty 文本输入里的换行由消费者展开成目标终端的回车——ConPTY 上的 cmd.exe 只认 CR 提交命令行（LF 会被留在输入缓冲里，几条命令拼成一行）；POSIX 行规程（ICRNL）把 CR 转成 NL，同一份字节两边都对。裸字节走字节帧、不经展开；子进程的 stdin 是普通字节流，换行保持 LF。

### 4.2 两个会话核心

```
core/
  ports.py           端口定义（依赖倒置接缝）+ 内置模式标签 / Stream
  errors.py          领域错误
  scan.py            转义序列与多字节字符的边界扫描
  journal.py         输出字节日志（真源）+ 对齐纯函数 plan_attach
  session/
    state.py         SessionState / 状态机
    base.py          Session 抽象：身份 + 生命周期 + 摄入 + 视图 + 尺寸事件
    registry.py      会话注册表（uid 主键）
    subscription.py  订阅者游标：从日志补齐 + 重建（不认识订阅者）
  terminal/          Pty 会话核心（特化）
    session.py       TerminalSession
  process/           子进程会话核心（特化）
    session.py       ProcessSession
```

`Session` 抽象持有共享逻辑（生命周期、日志、摄入、视图），通过端口调用宿主；`TerminalSession` 与 `ProcessSession` 只实现各自的输出流数与模型喂入。

**摄入在核心层闭合**：`Session.ingest_stream(stream, data)` 在内部完成"喂终端模型 + 追加日志"，保证 `fed_offset == journal.end`（重建路径正确性的前提），并返回本次的 offset 区间与模型要回写的应答字节。消费者据此推送、据此把应答交给写线程——核心层不关心谁在订阅。

### 4.3 生命周期管理

```
created ──start()──→ starting ──spawn 成功──→ running
                                    │
running ──子进程退出──→ exited ──close()──→ closed
running ──stop()/kill()──→ exited ──close()──→ closed
starting ──spawn 失败──→ closed（error 记录原因）
```

- **会话是守护进程的一等对象，生命周期与任何连接无关**：attach / detach、客户端断开都不影响会话；子进程退出**不销毁会话**，退出码与日志保留，仍可继续订阅与查询。
- 只有显式 `close`（或守护进程退出）才真正拆除并释放资源。
- 释放时机集中在一个显式的状态机里，不散落到各调用点。
- **"退出"与"排空"是两件事**：`exit_code` 一拿到就记（**`stop()` 只同步查一次、不做时序等待**——等待属于驱动方的 `refresh()`；`drained` 以**状态**为准，不依赖退出码，否则强杀后拿不到退出码就会让等待方死等），但"不再会有输出到达"要等所有输出流 EOF（`drained`）。进程退出与尾部输出到达之间有竞态，把两者混为一谈会丢掉最后一段输出。EOF 由驱动方（读线程 / 泵）打标记，但**排不排空由宿主回答**（`poll_eof()`）——**EOF 不等于退出**，程序可以先关掉 stdout/stderr 而继续运行。
- **注册表里只有活着的会话**：`SessionRegistry.create` 创建并启动，**启动成功才入表**；宿主建不起来时异常向上抛，表里不留残骸。`close_all` 逐个隔离——一个会话收尾失败不挡其余的。

### 4.4 输出字节日志（真源）

会话产出的原始字节按到达顺序追加到日志，构成唯一真源。

- **offset 从 0 起、单调递增、永不回退**；区间语义统一为半开 `[start, end)`。
- 日志有内存预算，超预算时从头裁剪；**裁剪点必须对齐转义序列边界**（否则重放会从序列中间切断，产生可见乱码）。
- 客户端游标若落后到已裁剪区间，服务端**不静默丢弃**：直接给一份重同步快照，并用一条 `resync` 通知标明（`lossy` 说明被裁的那段找没找回来）。**不让客户端再往返一次"我要重同步"**——推送模型里它本来就不是驱动方。
- **热状态**（屏幕内容、光标、SGR）与**冷状态**（备用屏、字符集、tab stops、键盘栈）都由字节流决定，因此新客户端整段重放 `[0, end)` 即可还原到与"从头就在的客户端"逐字节相同的状态，无需逐个状态保存与恢复。

### 4.5 返回数据（派生视图）

所有返回数据都是从真源派生的视图，按需生成、不额外维护状态。

**字节视图**（直接切片日志，每流独立）：

- 字节流全量
- 最后 N 行 / 指定行范围
- 最后 N 字节 / 指定字节范围
- offset 增量（自上次游标起的增量）
- 正则匹配（原始字节）

**屏幕视图**（Pty 会话，经终端模型渲染）：

- 可见屏幕纯文本（`screen_text`）
- 全量输出：含滚动历史的可见文本（`full_text`）
- 可见屏幕的字符格栅（`screen_cells`，宽字符的续格为空串）
- 屏幕 SVG / 位图（`render_svg` / `render_image`，可见区）
- 终端元数据（`metadata`：标题 / cwd）。**标题目前是占位值**——底层 `pywezterm` 的 `get_title()` 是哑接口（恒返回它自己的默认值），拿默认值冒充真标题会误导；`cwd` 走 OSC 7，拿不到则退回会话创建时的目录。

屏幕视图只在 Pty 会话存在；终端模型由所有者线程独占，喂入的字节与日志同源（见 4.7 的不变量）。

**"全量输出"只有一个含义**：含滚动历史的所有可见文本；字节侧的对应物叫**字节流全量**。由这些原料派生的返回数据（屏幕 diff、可见屏幕第 N 列）与判定（回显抑制）都在消费者——核心层只出原料。`rebuild_bytes()` 不在返回数据之列，它是订阅者重同步用的重建字节（见 4.6）。

**渲染结果的尺寸自带**：`render_image(scale=1.0)` 出的位图与 `render_svg()` 出的矢量都会把 1.0 倍下的像素尺寸写在输出里（PNG 的 IHDR、SVG 根元素的 `width` / `height`）。所以想按画布缩放的一方**从渲染结果自己读**即可，不必去别处问"字符格基准是多少"。

**尺寸变更是有序的**：`resize` 会在**输出字节日志的 offset 空间**里记一条 `ResizeEvent(offset, cols, rows)`——该 offset 起（含）的字节按新尺寸解释。订阅者随 `Pull` 一并拿到落在本段里的尺寸变更，据此在字节流里插帧。少了它，落后的 raw 订阅者会拿新尺寸去解释旧字节。没有屏幕的会话恒为空。

### 4.6 订阅与同步

**核心层提供订阅的机制，消费者持有订阅的关系。**

核心层给两件东西：

- **`Subscription`（游标）**：它记住"这个订阅者拿到哪了"，并按游标从字节日志补齐。对齐决策（`plan_attach`）在构造时做一次——游标在保留区内就续传，早于保留区就**重同步**（终端会话从终端模型重建完整快照；子进程会话没有模型、被裁的字节找不回，只能从保留区起点给，此时 `lossy` 为真）。构造**之后**游标又被裁（订阅者太慢）时 `pull()` 抛 `OffsetTrimmed`——**绝不静默丢弃**；消费者据此**换个新游标**（构造时自带快照），先把 `resync` 推给客户端再推快照。
- **`pull(max_bytes)`（分片拉取）**：一次只取至多 `max_bytes` 字节，剩下的留在日志里下次接着给。不设上限就是一次把日志尾部整段复制出来（预算默认 8 MiB），慢消费者要么一口吃下、要么自己切片，而内存里已经先复制了一份——"每轮按预算处理"因此落不了地。返回的 `Pull{start, data, resizes}` 里还带着落在本段里的尺寸变更（见 4.5），**重建快照同样受上限约束**（否则"重同步"那一次仍是一次性全量）。
- **`Wakeup`（唤醒）**：读线程读到数据（或某路 EOF）时投一个信号，驱动方阻塞等它——因此不必定时轮询所有会话。信号是提示不是账本：漏掉或重复都不影响正确性（醒来后照样按游标补齐）。

**为什么这两件归核心层**：游标是**读位置**，而读位置所在的 offset 空间（单调、半开区间、裁剪点对齐转义序列边界）本来就是核心层的语义。让消费者自己算，等于把这些语义泄漏出去；而且漏掉重建就是**静默丢头部**——最难查的那类 bug。

**消费者那侧只剩"依赖外部连接"的两件**：

- **订阅表**：谁订阅了哪个会话的哪一路。它绑着连接、有生命周期（客户端断开要注销），所以是"关系"，归消费者。
- **出站队列 / 发送循环**：把 `pull()` 出来的字节按协议发出去；队列满就停止 `pull`（见 §12）。

判定归属的一句话：**核心层持有的东西必须只依赖"会话自身"；一旦依赖"外部连接"，就归消费者。**

- 每个订阅者持有 `next_offset`（它下一个需要收到的字节偏移）。有新输出时，从其游标补齐到日志末尾，补到哪推进到哪。
- **拥塞只让推送暂停，绝不丢字节**：没推的部分留在日志里，队列排空后从游标继续。**只有这一道闸**——背压靠"投递是否被收下"传导（见 §12），不需要客户端 `ack`。
- 新订阅者视作游标 0；若 0 已落到已裁剪区间（`start_offset > 0`），与落后游标一样走重建字节重同步。

### 4.7 端口定义（依赖倒置）

核心层定义它需要宿主提供什么，`core/runtime/` 提供实现：

```
# 共同生命周期
HostLifecycle:  read(max_bytes, timeout) / write(data) / try_wait() / poll_eof(stream)
                kill() / close()
                descendants() -> 进程树成员 pid（轮询式观测，不含根进程）
                pid

# 终端宿主（Pty）
TerminalHost:   ingest(data) -> response_bytes     # 喂终端模型，返回要回写应用的应答
                resize(cols, rows) / metadata()
                rebuild_bytes()                    # 重建字节（重同步用），不是屏幕内容
                screen_text() / full_text()        # 可见屏幕 / 全量输出（可见文本）
                screen_cells()                     # 字符格栅（宽字符续格为空串）
                render_svg() / render_image(scale, fmt)   # 屏幕视图（可见区）

# 子进程宿主
ProcessHost:    read_stderr(max_bytes, timeout) / close_stdin()
```

**线程归属是端口契约的一部分**（方法按允许调用的线程划分，而不是按功能划分）：

| 方法 | 唯一允许的调用者 |
|---|---|
| `read` / `read_stderr` | 读线程 |
| `ingest` / 屏幕视图读取 / `resize` / `refresh` | 事件循环线程 |
| `write` | 写线程 |

由此得到两条可断言的不变量：`ingest()` 与日志追加在同一线程**相邻执行**，故 `fed_offset == journal.end`；因此读取屏幕（`screen_text()` / `rebuild_bytes()` 等）期间不可能有 `ingest()` 插入，读到的恰是"重放 `[0, end)` 之后"的状态。

## 5. 宿主实现 `core/runtime/`

**宿主侧的原生扩展（`pywezterm` / `resvg_py`）只在这里**；上层唯一的例外是验证台 `example/ui`——Tk 的 `PhotoImage` 没有 SVG 解码器，它自己栅格化。

```
core/runtime/
  vendor.py           把不安装的长期依赖接进 sys.path（在任何 import 之前完成）
  pywezterm_pty/      `pty` 宿主（惰性导入，纯子进程场景不碰）：pywezterm 一体
                      host.py 宿主（PTY + 终端模型）
  local_pty/          `localpty` 宿主（惰性导入）：平台原语（condrv / openpty）+ pyte
                      host.py 宿主 / screen.py 模型适配（含交替屏与重建字节）/ svg.py 渲染
  subprocess/         `subprocess` 宿主：Popen 双管道，无终端模型
                      host.py 宿主
  host_factory.py     按模式标签选宿主 + 启动期依赖检查
  process_tree.py     进程树：创建时即入作业 + 强杀 + 成员枚举
                      （Windows 查作业对象 / Linux 读 /proc）
  monitor/            监控：probe.py（跨平台入口）+ windows.py / posix.py（平台实现）
  bridge.py           读线程 → 所有者线程的有界桥（背压落点）+ 跨会话唤醒通道（`Wakeup`）
  reader.py           每路输出一个读线程
  runner.py           单会话驱动：读线程 + 写线程 + 所有者侧 pump()（交出本轮事件清单）
  input_queue.py      输入队列：按字节计量的双水位（唯一写者消费）
  runtime.py          会话运行时：会话 + 驱动成对管理、两阶段释放
  shell.py            平台默认 shell（起 shell 会话用）
```

单实例锁已提成**公共原语**（`foundation.instance`——消费者也要靠它分辨"守护进程在不在"），信号留在 `daemon/platform/`——它们都是进程外壳的活，不是"运行程序的能力"。

- **会话运行时 `Runtime`**：把会话与它的驱动**成对**管起来，并收掉两阶段释放。三个注入点——`registry=`（会话表）、`wakeup=`（唤醒通道）、`runner_factory=`（驱动构造；**给了就接管全部参数，含 `wakeup`**，与 `SessionKind.host_factory` 同一个规矩）。输入队列的水位就是这样由装配方定的：验证台注入小水位，才碰得到 `HOLD` / `REJECTED`。

- **终端宿主**：`pywezterm.Pty`（PTY）+ `pywezterm.Terminal`（wezterm-term 终端模型）。PTY 读与模型喂入分离到不同线程（见 4.7）；PTY 写在放掉 GIL 后做阻塞写。
- **localpty 宿主**：平台原语（Windows 走 `vendor/condrv` 的 ConDrv 直连，Linux 走 `vendor/openpty` 的 `os.forkpty`）只出 PTY 与字节，屏幕语义全在 `pyte` 侧。**`pyte` 不实现交替屏**（只把 `?1049h` 记进 `mode`），宿主里补了一层；重建字节也从 pyte 的格栅自己拼。
- **子进程宿主**：`Popen` 双管道，`start_new_session` / `CREATE_NEW_PROCESS_GROUP` 让子进程自成进程组。读用**带超时**的方式而不是纯阻塞（PTY 在子进程退出后不返回 EOF，纯阻塞会永久挂住线程）。
- **进程树**：Windows 用 Job Object 并设 `KILL_ON_JOB_CLOSE`——句柄一关（进程死），作业内残余进程由内核收掉。**作业在 spawn 之前建好、子进程创建时即入作业**（PTY 走 `PROC_THREAD_ATTRIBUTE_JOB_LIST`，子进程走 `CREATE_SUSPENDED` → 入作业 → 恢复）：创建后再 `AssignProcessToJobObject` 有时间窗，子进程在此期间 fork 出的孙进程会逃出作业，从此既枚举不到也杀不到。Linux 让子进程自成进程组（`start_new_session`），强杀时按组发信号。
- **进程监控**：进程树成员由 `descendants()` **轮询式**给出（Windows 查作业对象的进程列表，Linux 读 `/proc/<pid>/task/*/children`）——上层比对前后两次结果即可得出"谁起来了、谁没了"。代价是**可能漏掉两次轮询之间"起又没"的短命进程**。GUI 窗口探测只有 Windows 能可靠实现（`EnumWindows` 把窗口归属到 pid）；POSIX 上 Wayland 不允许客户端查询其他进程的窗口，因此返回 `None` 并记一条告警——**`None`（查不到）与空元组（确实没有）是两回事**，这是已知且刻意的能力差异，不是错误。
- **命令归一化**：工厂入口统一把命令归一为 `argv` 列表，后端只消费列表。

## 6. 守护进程 `daemon/`

**它没有业务代码，也不实现网络。** 它管三件事：

1. **自身的生命周期**：装配顺序即依赖顺序——取单实例锁 → 依赖检查 → 数据目录与日志 → 构造请求处理层 → 挂接入点 → 装信号 → 进循环；每一步都能回滚，停止时逆序收尾并带整体超时兜底。
2. **承载核心层**：把 core 装进这个进程，并做唯一的**所有者线程**。
3. **装配**：自带装配层与**默认请求处理层**，因此 `daemon/` 就是"能跑的那个进程"。

**它只由用户支配**：启动、配置、收尾都发生在 `daemon/` 的入口里（`python -m agentic_tty.daemon`——实例名是 `config/` 里的常量；**唯一的选项 `--cwd` 是"从哪儿起"，不是配置**）。**消费者格——包括验证台——不得启动它**：它们只被**告知**要连哪个名字，然后自己算地址去连；不拉子进程、不给它传参、不替它决定叫什么。（`tests/` 里起守护进程是为了测它本身，用的是它自己的接口，不算"支配"。）

```
daemon/
  __init__.py     包声明（说清它不实现网络）
  errors.py       守护进程错误
  handler.py      请求处理接缝：RequestHandler 协议 ＋ Reply
  server.py       Daemon：装配顺序、所有者循环、启动与收尾
  platform/       进程外壳的平台隔离：信号（单实例锁已提成公共原语 `foundation.instance`）
  ── 以上是"机制"：一行 core 都不许碰 ──
  kernel.py       默认请求处理层：uid 级请求 → core
  assembly.py     装配层：建 kernel → 交给 Daemon → 挂接入点 → run()
  __main__.py     入口：python -m agentic_tty.daemon [--cwd <目录>]（实例名是 config 里的常量）
```

**配置对象不在这里**——`DaemonConfig` 住在 `config/daemon.py`，这一层从配置包 import 它。

### 6.1 接入点

守护进程对外只有一个口子：**本机接入点**（命名管道 / `AF_UNIX`，落在 `transport` 的 `pipe://` scheme 上），由 `daemon/` 直接持有并挂监听。

- **它不是网络**：不开 TCP 端口、外部不可达。这是"核心层不实现网络"与"消费者可以连进来"两条并存的方式。
- **一个名字、多条连接**：同一个名字上可以同时接多条连接，每条是独立的一条双向字节流——这是"多个消费者连同一个守护进程"的底座。（Windows 命名管道按实例准备、一次只备一个，所以连接是"收下一条才腾出下一个"，接入点每轮 accept 一批。）
- **答复不在接入点里直接写**：每连接一个**按字节计量的有界出站队列** ＋ 一个写线程。队列满就拒收（`Delivery.CONGESTED`），由处理层停掉该订阅的 `pull`——**不阻塞所有者线程、也不丢字节**（见 §12）。
- **名字是算出来的，两端各算一次**：`config.constants` 从**实例名**派生出运行时目录、端点名（带项目前缀）与锁名——所以两端必然算出同一个地址，不需要任何发现协议。接入点地址由**实例名**派生（`DaemonConfig.name`）；`DaemonConfig.mount_endpoint` 只管挂不挂。地址**必须带运行时目录**（`pipe_address(endpoint_name(...), runtime_dir(...))`），`transport` 不猜默认值。守护进程侧**只在 `Daemon` 构造时算一次**、由 `Daemon.address` 给出，装配层与请求处理层都不预测它——预测错了不会报错，只会静默连不上。
- **就绪 = 能连上，不写任何就绪文件**（连 pid 文件也没有）。挂监听排在"构造请求处理层"**之后**，所以**连得上就一定服务得了**；客户端连不上就**重连**，不需要谁来发布状态。锁也回答不了这件事——它在装配的**第一步**取（那时还没监听），而且它是守护进程的内部机制，客户端不该碰。

### 6.2 请求处理接缝（不透明）

守护进程**只认一个注入的请求处理协议**（`handler.RequestHandler`），它不知道 `sid`、等待引擎、订阅这些东西的存在。

```
handle(request: object) -> Reply | None   # None = 已登记等待，稍后由 poll 交出
poll() -> list[Reply]                     # 交出此刻可以回答的答复（订阅推送也走这里）
pending() -> int                          # 还有多少条请求压着等（**订阅不算**）
failure(request, error) -> Reply          # handle 抛异常时转成一条明确的失败答复
on_input(key, data)                       # 接下一段上行字节
pump()                                    # 按轮推进
wait(timeout)                             # 空闲钩子：阻塞到"可能有活"，或超时
on_reply(request, delivery)               # 一条答复的投递结果（订阅推送的节奏靠它）
on_disconnected(connection)               # 一条连接没了：注销挂在上面的订阅
shutdown()                                # 收尾
```

**空闲等待由处理层提供**（`wait`）：所有者循环没有别的事可等时调它，实现方在这里等自己的异步工作（默认那份等的是核心层的 `Wakeup`——会话输出一到就立刻返回）。因此循环**被"有活"驱动**，不靠定时器轮询；`tick_interval` 只剩"接入点最多隔多久被看一眼"这一个作用（接入点在循环里**非阻塞**收）。

**订阅推送走延迟答复**：`subscribe` 的那条请求被登记下来（`handle` 返回 ack，此后每轮由 `poll` 按游标交出字节帧），**订阅 id 就是那条请求的 `mid`**——`Reply.request` 带着连接，答复因此自动回到对的那条连接。投递结果由 `on_reply` 回告：没被收下（连接堵住）就不再 `pull`，游标停住（见 §12）；连接没了由 `on_disconnected` 注销（写线程也会关连接，所以统一由所有者线程转达）。

**推送的成帧**：尺寸变更（`ResizeEvent`）可能落在这一段字节**中间**，所以按它把字节**切开**再发——订阅者收到的是「旧尺寸的字节 / resize 帧 / 新尺寸的字节」，**不必自己去对齐 offset**（core 只负责把 `Pull.resizes` 与字节放在同一个 offset 空间里，切片是这一层的事）。

**接缝上的报文对它是不透明的**：`object` 进、`Reply{request, answer}` 出，守护进程不解释内容。因此：

- 它的**机制不 import `core`**（白名单见 §3.4）；它 import `protocol` / `transport` 只为**装帧与搬字节**——接缝上的报文它一概不解释。换掉实现这一协议的那一方，机制一行不改。
- **两条请求通路**：接入点上的请求**已经在所有者线程上**，直接交给处理层，不经队列；跨线程投递（进程内消费者）走有界入站队列，队列满时投递方等待、背压传回消费者。接入点若也走队列会自锁——队列唯一的排空方就是同一个所有者线程，一轮里投进来的条目一旦超过队列长度就会死等一个永远轮不到的出队。
- **上行字节是单向的**：`on_input` 不产生答复，且只认"输入"这一个流标签（`STREAM_STDIN`）——拿下行标签冒充上行算对端的错，接入点关掉那条连接而不是静默丢弃。输入队列的判定（越软水位 / 超硬上限）由处理层自己消化；要把它变成给客户端的 `InputHold` 或断连，得由消费者在接缝上加一条回路（见 §12）。
- **延迟答复必须带回发起它的那条请求对象**：`mid` 只在一条连接内唯一，不能当全局键；兜住"这条答复回哪条连接"的，是请求对象的身份。
- 接缝**不透明**还有一个好处：把它从"进程内调用"换成"跨进程投递"，要动的只是"谁提供 `submit` / 谁接 `on_reply`"，`Daemon` 与 `core` 一行不用改。

### 6.3 单实例

守护进程**强制单实例**。理由是硬的：会话坐标（offset、日志、订阅表）活在单进程内存里，两个守护进程会各自维护互斥的 offset；接入点名字也会冲突。

- **Windows**：命名互斥体（`CreateMutexW`），内核对象，进程退出自动释放。
- **Linux**：`flock` 锁文件（或抽象 `AF_UNIX` 占位）。
- 实现位置：`foundation/instance.py`——它是**公共原语**：只管互斥、不认名字（锁名由 `config.constants.lock_name()` 给），因此消费者也能只读地问"这个实例在不在"。
- 锁名带命名空间（`Local\<实例名>-<目录 hash>` / `<运行时目录>/<实例名>.lock`），让多用户与同机多份配置共存；**不提供关闭单实例的开关**。
- 锁随进程退出由内核释放，因此**不需要额外的 stale 锁检测**。
- **`is_held(name)` 是只读查询**：不建文件、不留副作用。它回答"**在不在**"（正在初始化也算在），**不回答"能不能连"**——那是端点的事。两个信号合起来正好是**三态**：

  | 状态 | 单实例锁 | 端点 |
  |---|---|---|
  | 未启动 | 空 | 连不上 |
  | 正在初始化 | **被占** | 连不上 |
  | 已连接 | 被占 | **连得上** |

### 6.4 启动（严格有序，失败逆序回滚）

1. 取配置：`DaemonConfig` 是**显式对象**，字段默认值就是 `config/` 里的常量——**没有别的地方可配**（不解析命令行、不读环境变量、不读文件）。
2. 取单实例锁（最早取，避免两个进程同时初始化）。
3. 依赖检查（由装配层注入的检查函数）：原生扩展能否导入。不能 → **拒绝启动**，日志说明怎么补——绝不"起来了却建不出会话"。
4. 准备数据目录与日志（`config.constants.runtime_dir()`；锁 / 端点 / 日志都落在这一处）。
5. 装配：**请求处理层**（`daemon/kernel.py`，其中装 `core`，会话注册表默认宿主工厂来自 `core/runtime`）→ 交给 `Daemon`（它在构造时算一次接入点地址并交给请求处理层，在 `start()` 里挂接入点）。装配顺序即依赖顺序；这一步在 `daemon/assembly.py` 里。
6. 任一失败 → 关闭已装的，按逆序回滚，退出。
7. 装信号处理。
8. 进所有者循环。

**从第 5 步挂上接入点那一刻起，外面就"能连上"了——那就是就绪，不另写就绪文件。**

**`--cwd` 不是配置**：它是"**这一次从哪个目录起**"（守护进程开的会话默认就在那儿；不给 = 继承你敲命令时所在的目录），属于**怎么起**，不属于**实例身份**——所以它走命令行，不进 `config/`。会话自己的目录另有 `create_terminal(cwd=…)`（见 §10）。

每一步都必须能回滚：已装的接入点要关、已起的线程要停、锁要放。回滚按逆序做，且每个撤除都**幂等**——不必记账，看当前装了什么就撤什么。

### 6.5 运行与停止

- 所有者循环驱动：接入点收请求 → 交给请求处理层；`pump()` 推进会话；答复交回。**所有会话状态都只在这个线程上改动**，因此核心层与请求处理层都不需要锁。
- **会话生命周期与守护进程解耦**：客户端 attach / detach、子进程退出，都不销毁会话。
- 可观测：守护进程状态（pid、启动时长、会话数、接入点、配置摘要）与日志轮转。
- **不做配置热重载**：配置在装配时注入，改配置必须重启，避免"一半新配置一半旧配置"的中间态；会话级配置可运行期改。
- 停止：关接入点（不再接新连接）→ `draining`（不再处理新命令，在途的给一小段时间跑完）→ 会话收尾（**先强杀进程树，再关宿主**；宿主关闭可能无界阻塞，整体带超时、放在线程里）→ 停读写线程 → 刷日志、放锁 → **整体超时兜底**。
- 强制退出由**装配层**（`daemon/assembly.py`）执行，不是库自己杀进程：`stop()` 带超时返回"是否停干净"，装配层拿到否就强制退出。
- 崩溃：Windows 靠 Job Object 的 `KILL_ON_JOB_CLOSE`、Linux 靠进程组，保证会话不留孤儿。
- **崩溃后不假装恢复**：offset、字节日志、终端模型全在内存里，重启后客户端拿到"会话不存在"，客户端重连重建。

## 7. 客户端命令处理层（消费者）

**直接连核心层、回应请求的那一层。** 它自己对外开服务器，服务客户端 cli / 客户端 mcp / mcp 层 / CLI 层。

**它是一个独立进程**：与守护进程同机、经 `pipe://` 相连；与它自己的客户端则可能跨机（`tcp://`）。**`sid` 在这一层才诞生**——守护进程侧的协议载的是 `uid`，这一层持 `sid ↔ uid` 的映射。

```
<消费者>/
  directory.py        会话目录：sid ↔ uid 映射 ＋ tags / 会话级配置
  sessions.py         会话管理：创建 / 查询 / 列表 / 关闭；全局默认值与会话级值
  conditions.py       返回条件词汇与匹配器
  wait.py             等待引擎：把返回条件喂给会话输出，判定何时返回
  subscriptions.py    订阅表（谁订阅了哪个会话的哪一路）+ 出站队列 / 推送
  dispatcher.py       命令分发：把统一命令映射到用例，解析返回条件为 WaitSpec
  plugins/            插件系统（宿主 + 注册表 + 钩子引擎 + 清单校验）
  notify.py           通知：异步返回结果的存储与取回
  （配置对象住 `config/`——这一层自己的字段往 `config/consumer.py` 上加）
```

- 核心层只认 `uid`；`sid` 是**这一层**的语义，由会话目录持有映射。前端一律说 `sid`，目录翻译成 `uid` 发往守护进程；守护进程的事件带 `uid`，目录翻译回 `sid` 再发给前端。**经这一层的 mcp 层与 CLI 层都通过同一套 `sid` 拿到一致的会话身份**——这就是"统一会话管理层"的落点，不新增一层。
- **返回条件与等待引擎属于这一层**，不在核心层。

### 7.1 等待引擎

| 条件 | 语义 | 适用 |
|---|---|---|
| `notify` | **正交模式**：立即返回，其余条件挂后台继续检查，命中后推送事件 | 全部 |
| `matched` | 正则命中 | 全部 |
| `ended` | 程序退出 | 全部 |
| `crashed` | 程序异常退出 | 全部 |
| `timeout` | 显式超时（兜底） | 全部 |
| `idle` | 静默超时（兜底）：Pty 看**可见文本**是否变化，子进程看**字节流**是否静默 | 全部 |
| `gui` | 检测到 GUI 窗口（异常） | 全部 |
| `echo` | 屏幕/字节流回响命中，用于精确判定命令结束 | 全部 |
| `cancelled` | 被显式取消 | 全部 |

- **`notify` 不是与其它条件并列的选项，而是可叠加的模式**：`notify` + 其它条件 = 立即返回 + 后台继续检查 + 命中后推送事件。
- 求值优先级固定：`cancelled → matched → crashed / ended → idle → timeout`。`matched` 排在退出之前是刻意的：trigger 是用户的显式诉求，一旦出现就定案；`ended` / `crashed` 是兜底。
- **结束以核心层的 `drained` 为准**：进程退出与尾部输出到达之间有竞态，必须等核心层把"退出 + 全部流 EOF"合起来判定，否则会丢掉最后一段输出。
- **等待装载之前到达的输出不能丢**：装载时先用会话已积累的输出试一次匹配——短命令（"打印标记后立刻退出"）的输出与退出都可能发生在装载之前。
- **回显抑制**：正则匹配必须区分"程序回显的输入"与"程序真正的输出"，利用两者在字节结构上的差异做判定。
- 子进程会话不适用屏幕相关的条件（`echo`）。

**引擎位置**：判定所需的原料全部来自核心层——输出由**核心层的驱动**（`SessionRunner` 的读线程）读入并记账（`ingest_stream`），退出与排空由核心层判定（`exit_code` / `drained`）。这一层**不碰 `read_stream`、也不调 `pump()`**（它在另一个进程）：它**订阅**要看的会话，由守护进程侧**按游标把增量字节推**过来（字节帧），据此推进等待判定与订阅游标。因此这一层不需要反向拉取数据流。

### 7.2 认证

**认证不作为独立一层存在。** MCP 不需要认证；CLI 的认证**内化在 CLI 层自身**（既不独立成层，也不放进公共层），凭证走信封上的 `auth` 槽。

## 8. 公共层

### 8.1 `foundation`

日志、错误基类、id / 时间戳、平台原语（实例互斥）—— 被 ≥2 层使用的无领域语义基础件。

### 8.2 `config`

**契约公共层：配置常量。** 两端必须一致的那些名字与参数都**写死**在这里，**没有别的地方可配**（不读命令行、不读环境变量、不读文件）——"两端各算一次必然一致"就建立在这上面。

```
config/
  constants.py   PREFIX · DEFAULT_INSTANCE ＋ runtime_dir / endpoint_name / lock_name
  daemon.py      DaemonConfig —— 守护进程的装配参数（字段默认值就是常量）
  consumer.py    ConsumerConfig —— 消费者：要连哪个守护进程
```

- **命名只此一处**：同一个实例在操作系统里叫什么（运行时目录 / 端点名 / 锁名）由这里算出来——**两端各算一次，必然一致**，所以不需要任何"发现"协议，也不需要谁发布状态。
- **它只压在 `foundation` 上**，所以 `transport` 够不着它：管道名是**完整名字**，前缀由 `endpoint_name()` 加。这是"transport 不认识命名习惯"的落法。
- **默认实例名 `DEFAULT_INSTANCE` 是两端共用的约定**，不是某一方的私产。要跑别的实例就改这个常量——**没有第二个地方**。

### 8.3 `protocol`

**两端之间唯一的契约**：通用底座（帧（控制 / 字节两路）、信封、响应约定、增量读帧器）＋ 按边界分区的消息 schema。它**认识**帧格式与消息模型，**不认识** socket、连接、超时。

```
帧：  ┌──────────┬──────────────────┬──────────────────┐
      │ 帧类型 1B │ 负载长度 4B(大端)  │ 负载 length 字节   │
      └──────────┴──────────────────┴──────────────────┘
```

- **控制帧**装 JSON 信封；**字节帧**装"流标签 ＋ 键 ＋ 原始字节"——字节不走 JSON，否则每个字节都要 base64，白白膨胀三分之一。
- **流标签按方向定**：下行是 `stdout` / `stderr`，上行是 `stdin`（输入只有一个方向，这个标签只为把上行与下行同型帧区分开）。接入点校验上行标签——拿下行标签冒充上行算对端的错，关连接，不静默丢弃。
- 信封字段：`proto / dir / type / mid / ts / kind / auth / payload`；载荷分四组（操作 / 返回条件 / 返回数据 / IO）。
- 单帧负载有上限——长度字段是对端给的，不设上限等于允许它让我们分配任意大的内存。
- **报文编解码只属于这里**：跨进程 / 跨机时把请求与答复变成字节，靠的就是这套契约。
- **按边界分区**：通用底座（`frame` / `envelope` / `response` / `errors`）谁都 import，自己不认识任何边界；消息 schema 按边界各占一份（`contracts/daemon_ipc.py`、`contracts/consumer_ipc.py`），**两份互不依赖、互不共享类型**。具体层只 import 它需要的那一份。
- **`FrameReader` 也在这里**：解码器只做"字节 → 帧"，从哪拿字节由装配方注入一个"返回 bytes 的函数"。因此这一层拿到读帧的能力，却不因此认识连接、超时、socket —— 帧与传输的缝合发生在装配点，不在任何一层里。
- **错位即作废**：`FrameReader` 抛过 `FrameError` 之后就再也读不出东西。信封是在读帧之后由调用方解的，它抛的 `EnvelopeError` 属同一类（`ProtocolError`），所以"这条流作废"在调用方那一侧同样成立——**拿到 `ProtocolError` 就断连、丢掉这个 reader**。

### 8.4 `transport`

**让能力可以被进程外访问的那一层，覆盖同机与跨机两种形态。** 这一层是**两侧共用的同一份实现**：服务端调 `listen()`、客户端调 `connect()`，差别只在调用哪个方法；共享的是**实现**而不是进程。

**按地址 scheme 分派**——加一种传输方式只动注册表：

| scheme | 实现 | 用途 |
|---|---|---|
| `tcp://` | TCP | 消费者对各自客户端开服务器；跨机由监听地址 + TLS 决定 |
| `pipe://` | Windows 命名管道 / POSIX `AF_UNIX` | **守护进程的接入点**；本机，不是网络 |
| `shm://` / `stdio://` | 预留 | 按同一机制接进来 |

- 对外形状与实现无关：上层拿到的永远只是一个 `Connection`。
- 传输形态**只在地址里体现**，不在任何上层代码里体现。
- **它不认识命名习惯**：`pipe://` 的 netloc 就是**完整名字**（前缀由 `config.constants` 加），且地址**必须带运行时目录**——不猜平台默认目录（猜出来的未必是守护进程待的那个，那是静默的错）。
- 平台差异（命名管道 / `AF_UNIX`）全部收敛在这两个实现里，上层不写平台分支。

## 11. 线程模型

**所有会话状态（含终端模型与日志）只在事件循环线程上改动；PTY 写只在写线程上发生。** 并发正确性靠"单线程所有者 + 唯一写者"，而不是加锁。

```
读线程 ──有界桥──→ 事件循环 ──出站队列──→ 发送循环 ──→ 连接
   ↑                  ↑
host.read()      Session.ingest_stream()（喂模型 + 追加日志，相邻、同一线程）
                      ↓
                 写线程 ──→ PTY（客户端输入 + 宿主应答，唯一写者）
```

线程账（每个会话）：

| 会话类型 | 专用线程 | 说明 |
|---|---|---|
| Pty | 2（读 1 + 写 1） | `Pty.read` / `Pty.write` 都是阻塞调用；且 `Pty` 未暴露 `fileno()`，Python 侧无法多路复用 |
| 子进程 | 3（stdout 读 + stderr 读 + 写 1） | 两路管道各一个读线程；写线程是唯一写者 |

所有者循环是**共享**的（不是每会话一个），默认 1 个，可横向分片（把一批会话挂到多个所有者循环上）。

- 写 PTY 单独一个线程：写是阻塞操作，不能压在事件循环上。
- 读桥有界：队列满时读线程等待，背压向 PTY 传导（进而让子进程写阻塞）。
- 读线程投递后经 `Wakeup` 唤醒驱动方——驱动方因此可以阻塞等待，不必定时轮询所有会话（见 4.6）。
- 宿主应答（DSR / 焦点应答等）必须无条件入队，否则模型永远收不到回复而卡死。
- **读与写不能合成一个线程**：子进程写满输出管道被阻塞时，若同时在阻塞写它的输入管道，双方互相等待，会死锁。

## 12. 负载与背压

**两道闸，各管一个方向；公平性不是闸，是循环的调度。**

1. **生产端（子进程吐得快）**：有界桥 + PTY 自身读缓冲水位。桥满 → 读线程等待 → 停止从 PTY 读 → 管道填满 → **子进程写阻塞**。背压最终落到子进程，服务端不无限缓冲。
2. **消费端（客户端跟不上）**：每连接一个**有界出站队列**（按字节计量）＋ 一个写线程。队列满 → 该订阅**停止 `pull`**（游标不动，**绝不丢字节**）→ 数据留在日志里；游标落后到裁剪点 → 重同步。**只有这一道闸**：背压靠"投递是否被收下"传导——客户端读得慢 → 管道满 → 写线程阻塞 → 队列满 → 投递被拒 → 游标停住。**不需要客户端的 `ack` 协议**：管道本身已经是有限缓冲，再加一层应用层窗口只是把同一件事做两遍，还多一条往返。

内存闸：字节日志按预算裁剪，裁剪点对齐转义边界。

**公平性**（不是闸，是循环的调度）：所有者循环每轮**按预算处理**（每会话每轮最多 N 字节 / M 个块），不把某个会话的积压一次倒完。

**卡住的两种情形**：

- **子进程不读 stdin**（写阻塞）：写线程独立，循环不受影响。输入队列按**字节**计量（`core/runtime/input_queue.py`），`submit_input` 返回三态：`QUEUED`（收下）、`HOLD`（收下但已越软水位）、`REJECTED`（超硬上限，整块不收）。**机制在核心层、策略在消费者**：核心层只出判定、字节深度（`input_depth`）与低水位放行（`input_drained` / `wait_input_drained`）；"给该客户端下发 `InputHold`（发送方本端排队）、超硬上限就断开那条连接"绑着外部连接，归消费者。**绝不用"停止读 socket"做背压**——那会把同一条连接上的控制面（关会话、取消）一起堵死。
- **子进程卡死**（要强杀）：`stop()` **先强杀进程树**（Windows Job Object / Linux 进程组），再关宿主——Windows 上 `host.close()` 可能要等控制台客户端退出（可达数百秒且持着 GIL）。**资源释放两阶段**：同步摘除（会话立刻从列表消失、不再扇出）+ 线程里释放（阻塞多久都不挡循环）。

**TUI 巨量输出**：不另设订阅模式。客户端按 `pull(max_bytes)` 自己控制每轮取多少；要跳过积压就直接**重同步**（丢掉中间字节、取当前屏幕——终端会话无损，子进程会话 `lossy`）。这比另设一套"服务端渲染快照"的模式简单，而且 core 也拿不出带属性的快照：`screen_cells` / `screen_text` 只有文本（丢了颜色），`render_svg` / `render_image` 比原始字节更大。

## 13. 目录结构


## 14. 依赖强制与测试

- **分层测试**：`tests/test_layering.py` 扫 AST 强制依赖方向——公共层不导入非公共层、`config` 只压在 `foundation` 上（`transport` 够不着它，所以它不持有管道前缀）、原生扩展只允许出现在各自的宿主格子里（`core/runtime/pywezterm_pty/` / `core/runtime/local_pty/`，验证台 `example/ui` 例外）、`daemon/` 的**机制**文件不得 import `core`（白名单只有 `kernel.py` / `assembly.py` / `__main__.py`；可以 import `protocol` / `transport`，且**只用 `transport` 的本机管道部分**）、任何包不得 import `example`、**消费者链只依赖公共层**（`foundation + config + protocol + transport`；由此消费者之间不可能互相 import）、`example` 内非验证台的格只许依赖公共层且不得跨格引用、**消费者格不得出现启动进程的调用**（守护进程只由用户起）、`protocol/contracts/` 的分区互不依赖、web 框架只允许出现在 web 层、**`vendor/` 里的自研模块不得 import `agentic_tty`**（它们是被依赖方）。
- **单测**：核心逻辑跑在假宿主（fake host）上，无需原生扩展与网络；假宿主的线程归属与真实宿主一致，因此订阅、补齐、裁剪、重同步、流控、条件判定都能被确定性测出。
- **契约测试**：接上真实 PTY + 终端模型后仍成立（进程启动 / 控制台附着 / 进程退出等真实操作系统事件）。
- **接入测试**：各消费者各自的端到端。
- **测试同步纪律**：不用固定睡眠等异步效果，用具名栅栏等待可观察条件；由测试机器化执行。

## 15. 实施顺序

顺序有一条硬理由：**请求处理层可以用替身顶上，所以它不必排在前面。** `daemon` 的机制只认注入的请求处理协议，于是 `protocol → transport → daemon` 可以先配一个演示替身把链路端到端跑通，正式的消费者再回头补齐——每一层都能单独验证。

1. `foundation` ＋ `core`（会话模型、日志、视图、生命周期）＋ 假宿主
2. `core/runtime`：终端宿主 ＋ 子进程宿主 ＋ 进程树
3. `config`：契约公共层——配置常量（名字前缀 / 默认实例名 ＋ 本机实例命名 ＋ 各层配置对象）
4. `protocol`：通用底座（帧（控制 / 字节两路）、信封、响应约定、增量读帧器）＋ 按边界分区的消息 schema
5. `transport`：字节流抽象 ＋ scheme 分派 ＋ **本机管道**（守护进程的接入点）
6. `daemon`：机制（单实例、依赖检查、信号、启动顺序与停止收尾含整体超时兜底）＋ **装配层与默认请求处理层**（`assembly.py` / `kernel.py` / `__main__.py`）
7. **守护进程的接入点**（`daemon/` 内，`pipe://`）：accept 多条连接、请求进接缝、答复按请求身份写回
8. 客户端命令处理层：会话目录（`sid ↔ uid`）、等待引擎的完整条件集、订阅编排、通知、配置、插件
9. `web` 层 / `mcp` 层 / `CLI` 层：各自对外开服务器
10. `transport` 增加 TLS 与跨机支持
